# A scene from a build sheet: the manifest

A **build sheet** lists what a scene does, a step at a time: a row for the step itself, then one row per thing that happens in it (the word `use`, its Target `DOOR`, its Clip `A02`), and a **delivery** carries what its steps act on (an FBX of the scene, one take per animated row). unitytk turns the two into a built Unity scene, and keeps it in line as either changes. Nothing here is specific to one kind of project: a row is read as a **behavior**, and a behavior is built by whatever builder a kit registers under its name. The [Tasks kit](tasks.md) is the first set of behaviors; a project adds its own beside it.

```
build sheet (CSV, or a sheet's URL) ─┐
                                     ├─ sheet.sync ─► plan.json + the delivery, staged under Assets ─► Manifest: Assess / Build ─► the scene
delivery (FBX: nodes and takes) ─────┘   Python: unitytk.sheets                                        C#: Features/Manifests, each row its kit's builder
```

The sheet is the one the [Shot Manifest](https://github.com/m3trik/mayatk/blob/main/docs/shot_manifest.md) builds shots from in the DCC, read by the same parser. The two manifests work hand in hand (a take the artist names from the sheet is the take a row plays here) and neither needs the other: this one reads the sheet itself, and a delivery from any tool.

## From a sheet to a built scene

0. **Start the sheet** (a new task). `python -m pythontk ops apply sheet.new out=<sheet.csv>` writes the Interactive template's starter (a small task that uses every word and passes the check) to rename and fill; `python -m pythontk ops run sheet.check sheet=<sheet.csv>` holds it to the format as it is written, before any scene exists.
1. **Stage it.** `python -m pythontk ops apply sheet.sync settings=<the sheet's settings file> project=<the Unity project>` reads the sheet into its plan and copies the plan, the delivery's files and each step's sound under the project's `Assets/<name>/`. Only what differs is written, so the same command is the first setup and every later update. `ops run` plans it and writes nothing. It refuses, before writing anything, a folder outside `Assets`, two delivery files of one name, and a sound that lies outside the settings file's folder; and where the sheet narrates, it says which voiced steps have no sound yet (`silent`, raised once with `narration.render` as its fix), since the task would be silent there. Narration is added after the fact the same way: render or record the lines beside the settings file, stage again, Build.
2. **Open its manifest.** In Unity, `Tools > unitytk > Manifest`, then **New...** and pick the staged plan: its manifest (a `Manifest` asset: the plan, the delivery's model, the scene the result is saved as, the locked steps, each kit's settings) is made beside it.
3. **Assess.** The table shows every step with its rows and where each stands in the open scene. Nothing is changed.
4. **Build.** The delivery is placed, every row that can be built is built, and the scene is saved as the manifest's. Adjust what a build placed, change the sheet, re-export the delivery: stage again and Build again. A build changes only what differs, and keeps what a person adjusted. **An update is two clicks in the window**: **Read the Sheet Again** (the notice that the sheet changed, or the **≡** menu) runs step 1's command for this manifest and imports what it staged, then **Build**. It needs the Python automation on the machine, as step 1 does; where it cannot be run the window says why and offers the command to copy.

**One task, however its inputs change.** A task is its settings file: staged, it names the folder, the plan (`<settings>.plan.json`), the manifest beside it and the objects its build makes in the scene (`Task (<settings>)`, `Placard (<settings>)`...). Everything the settings file points at is a version of the task, so an update is the same manifest built again, never a new one:

- **The sheet is edited, renamed or replaced** (a project manager's change): point the settings file at it where its name changed, stage again (the window says the sheet or its settings changed, with the command), render the narration of any reworded line (staging names the silent steps), and Build. Only what changed is rebuilt; a person's adjustments stay.
- **The delivery is re-exported under a new name** (a dated file): point the settings file at it and stage again; the plan is then read against it, and the next Build moves the manifest onto it, swapping the placed instance over (Unity's Replace Prefab Asset, each node matched by its place in the hierarchy), so what the build and a person put on its nodes stays. The window says so before the build. The staged copy it moved off goes, with its media folder, once nothing places it: an open scene, the manifest's own scene saved with it (not open), or another manifest beside it that builds it keeps it, and the build says which. A node the new export lacks loses what was on it: the exporter's hierarchy check (**New Nodes Pass**) stops such an export before it ships.
- **A new task** is a new settings file.

Build works in whatever scene is open, a new project's sample scene included, and leaves it playable: the delivery brings its own lighting (its lightmap set switches off the scene's lights that would light its baked surfaces twice, and lights the parts no map lights by the room its maps were baked in: [the package README](../com.m3trik.unitytk/README.md)), and a kit gives the scene what its rows need to run (the Tasks kit: a user's rig where the scene has none).

To try it with no sheet of your own: the [Tasks sample](tasks.md#the-sample-task-tested-then-played)'s demo makes its task's manifest beside its plan, so after `Tools > unitytk > Samples > Task Demo`, the Manifest window opens on it with every row built.

## The Manifest window

`Tools > unitytk > Manifest` is the launchpad for a sheet-built scene, and it shares its layout and its words with the Shot Manifest, so a person who knows one reads the other:

| Part | Holds |
|:---|:---|
| The manifest's row, at the top | The window's tab says what it is; its first row is the manifest (pick one, or **New…** from a plan), **Setup**, **?** (how it is used) and **≡** (its actions: Build in a New Scene, Open Scene, Show Asset, Revert All Edits; each behavior's switch for the whole manifest; the window's options). Under it, the sheet, the delivery and the scene it was read from. Notices follow: a plan that cannot be read, no delivery, a scene that is not the open one (**Open Its Scene**), and *the sheet changed since the plan was read* with **Read the Sheet Again**, which runs the sheet's reader from the window (the **≡** menu has it at any time, and **Copy the Read Command** for a terminal), or what of it could not be told (a file another program holds, a settings file this editor cannot read), and what the last run said that no row says (a refusal, a setup that failed), each with its own severity's mark. What a build says while it builds a row (an arrow with no free spot, a fade its step's return leaves out) is that row's warning, said on the row alone. A notice offers only what the toolbar does not: Setup is the toolbar's. |
| **Setup** | The manifest's own fields, each kit's settings (**Customize** gives the manifest its own, kept inside its asset; until then the kit's defaults build), and **Behaviors**: each behavior the plan uses with its switch for the whole manifest, what it does, and its own **Settings...**. |
| Select / Expand / Collapse / Hide / Show | The Shot Manifest's five menus: rows with issues, rows to build, the rows' objects in the scene; **Hide > Steps With Nothing to Do** is the Issues view, a view alone. A search field beside them. |
| The table | Step, Status, Section, Description, Behaviors, Objects: a line a step, and under it, on a darker ground, a line for each object its rows act on, as the Shot Manifest lists a step's objects. An object's Behaviors cell holds every behavior the step gives it, each led by its state's glyph in its colour (a green check built, a blue dot for Build to do, a sand triangle a warning, a red cross an error; grey and struck through where it is off, amber where this project added it); the step's own line holds the behaviors that name no object (it goes on by itself, it offers Next). A line's mark is its state's glyph in its colour (the same one its behaviors carry), the Status cell says it in a few words in that colour, and every cell's tooltip says why. |
| The detail, under the table | The selected line: the sheet's words, and a card for each of its behaviors: the row as the sheet writes it, what the behavior does, each issue (with **Copy** where its fix is the sheet's or the delivery's owner's), the parts it built, each with **Select** and **Edit** (the part's own editor, in a window of its own), what a build would change for it, and its switches (**Turn Off Here**, **Settings...**). With nothing selected: what a build would do as a whole, and what the steps share. |
| The foot | The summary, **Export** (the issues for the sheet's owner as Markdown, or the table as shown), **Assess** and **Build (N)**: the count of what a build would change, its plan in the tooltip. |

A row's status is one of these (`ManifestStatus`, the same words from code):

| Status | Says | Means |
|:---|:---|:---|
| `valid` | (a check) | Built, as the sheet says. |
| `missing` | not built | Not in the scene yet: Build makes it. |
| `update` | to update | The scene differs from the sheet here (a part taken away, a setting changed): Build brings it in line. |
| `locked` | locked | Its step is locked: Build leaves it as it is. |
| `missing_object` | not in scene | A name it uses is no node of the delivery. |
| `ambiguous_object` | ambiguous name | Several nodes answer to a name it uses. |
| `missing_take` | take missing | The delivery carries no take of the name it plays. |
| `sheet` | sheet issue | The sheet's reader could not read the row: its fix is the sheet's. |
| `unbuildable` | incomplete row | Its builder says it cannot be built as written. |
| `unknown_behavior` | unknown behavior | No builder has its behavior's name. |
| `warned` | warning | Built; something about it may be wrong. |
| `off` | off | Turned off in this project (its behavior, or this object's): Build leaves it out. |
| `added` | added here | Added in this project: the sheet does not give the object this behavior. |
| `adjusted` | adjusted here | Built, and a part it holds was changed in the scene since (a field edited, a helper moved: one a build placed, or one the delivery brought): every build keeps the change. **Revert** on the part gives it what the build gave it (a delivered helper: where its maker has it). |
| `upstream` | in the delivery | The delivery's own build made it on this object: keyed into the step's takes where the delivery was made (each shipped behavior's `mode: key`, the plan's `upstream`). Left to it, so the two manifests build each behavior once; the row's other objects are built here. |

The six before `warned` wait on a person: no build resolves them, the Build button never counts them, and Export collects them for whoever owns the sheet or the delivery. The window edits what the Unity project owns (the manifest, its kits' settings, its locks, which behaviors it builds, what a person adjusts in the scene) and nothing upstream: a sheet's fix is made in the sheet.

### Behaviors: several to an object, each with a switch and an editor

An object has as many behaviors in a step as the sheet's rows give it (the keys are highlighted, pointed at and taken in one step), and the window works them as the Shot Manifest does:

- **Give one or take one away.** Each behavior in the Behaviors cell is a chip in its state's colour, with its own tooltip; a chip says what tells its row from its behavior's others (`Goto 'YES' → B03_5`: its behavior's `ChipFields`), and its tooltip every field the sheet's row gives it, labelled as its behavior says (`FieldLabels`); click it for its own menu: **Turn Off for 'X'** (or back on), **Turn Off Everywhere**, **Edit** what it built, its **Settings…**, and **From the Sheet** (its choice, the step it goes to, its take, what is in hand). **Settings for 'X'…** gives that object values of its own: any of the behavior's settings over its kit's and its sheet's row's (a button held to play, an arrow's colour: `ManifestsActions.SetTune`, `Manifest.Tune.values`) and its row's fields over the sheet's (the take it plays, the step it goes to: what a behavior added here needs; `SetRowField`, `Manifest.Tune.fields`), kept apart and as an edit. A setting the behavior keeps for its row as a whole (`RowSettings`: a take's window and speed, one clip player entry whatever objects the row names) is offered for no object: **Settings > For Its Row…** gives the row its own, kept under it (an empty target) and said on each of its objects' chips, and an object one is refused for (`SetTune`, `unity.manifest.setting`); an object the manifest builds as a row of its own (added here, or given a take of its own: `IsOwnRow`) keeps them as its own (`ManifestsActions.Offered` says what each is offered). A name that is no setting of the behavior's kit is never dropped silently: in the sheet's row it is left out and said as a note on the row (`unity.manifest.note`); set here, it is refused (`unity.manifest.setting`). A behavior read several ways says which beside its name (*Pause · start*, *Marker · hide*, *Use · hold to play*). What you change in the scene on what a behavior built (an arrow moved, resized, recoloured) is kept at the next build as that object's own. **+** at the end of the cell adds one, as a checkbox list that stays open (what you tick is one edit as it closes): for an object, what its node alone can build; for a step, the behaviors that name no object (going on, a note). Every chip works alike, on a step's line and an object's. The sheet is not changed: the manifest keeps the difference as an edit (`Manifest.edits`; a step's own with an empty target), every build goes by it, the chip shows it (grey and struck, or amber), Export lists it for the sheet's owner, and **Revert 'X'** or **Revert All Edits** goes back.
- **Turn one off for the whole manifest.** The window's menu (**Behaviors**), or Setup's Behaviors list: a build leaves every row of a behavior that is off out (`Manifest.off`).
- **Open its editor.** For every row of a behavior: **Settings...** (the fields of its kit's settings the behavior says are its own, in a small window; kept in the manifest). For one object in one step: **Edit** on what the behavior built there (a highlight's colour, an arrow's size, a take's speed), from the cell's menu, the row's right-click menu or the detail's card.

**What you change in the scene stays, whatever the part.** Every build records what it gave each part it holds (the plain fields of its components: a number, a flag, a text, a choice, a colour, a vector). A field that differs from that record is a person's adjustment: where a page comes up, how long a press is held, a holdable's travel time, a page's wording. The window lists it on the part at once (its row reads *adjusted here*), the next build keeps it in the manifest (`Manifest.adjusted`) and builds over the parts as it last left them, so an adjustment is never work for a build and never undone by one; the sheet's or a setting's later change still reaches the part underneath it. **Build in a New Scene...** with the adjustments kept carries them over. **Revert** on a part's row gives it what the build gave it, and **Revert All Edits** takes every adjustment with the edits (`ManifestsActions.Adjustments`, `RevertAdjustments`). A field a behavior keeps as its object's setting (an arrow's size and colour) is that setting's instead, edited and reverted with the settings. **A helper you move is an adjustment too**: an arrow, a viewpoint or a picture's camera the build placed, moved or turned in the scene, is kept where you put it by every build (its kit keeps it, relative to the part it is placed by, so it follows the part in a new delivery), reads *adjusted here* on the row that placed it, and **Revert** puts it back where the build placed it (`IManifestKit.Kept`, `Revert`; `Placements.Restore`).

A step whose rows changed since it was built (one turned off or taken away, a row the sheet dropped, a take renamed) is wired anew by the next build: the kit keeps what each step was built from (`Step.source`) and empties a step's wiring where that differs, so nothing of a row it no longer has stays live. What the row built is left in the scene, switched off; **Build in a New Scene...** leaves it out altogether.

Two things are done otherwise than in the Shot Manifest, where they proved awkward: which behaviors are off is the manifest's, shared with the project (there it is each person's own setting, so two people build one scene differently); and a behavior says itself what its settings are and what it built (`[ManifestBehavior(..., About = ..., Settings = ...)]`, `scene.Hold(part)`), so the window names no behavior (that panel knows each behavior's editor by name).

- **It stays current.** A change in the scene, an undo, a plan staged again: the window assesses again by itself while an assessment is quick; on a large scene it says the scene changed and leaves Assess to the person (the menu's *Assess as the Scene Changes*).
- **An assessment is the build's own dry run.** A row with nothing to change is built; a row with changes says them (the detail's *Build would*). So what the table says and what Build then does cannot differ.
- **A row leads its right-click menu with its own fix**: **Build** for the steps to build (those steps alone; what the steps share is built with them), **Copy the Fix** for a row that waits on a person. Then **Select in Scene**, **Frame in Scene**, the line's behaviors (ticks, **Add**, **Edit**, **Settings...**), **Place Again** for a part a kit placed by a search (an arrow, a viewpoint, a picture's camera: its first placement and any move a person made of it go, and the next build searches anew; `ManifestsActions.PlaceAgain`), **Lock Step**.
- **Selection goes both ways.** Double-click a line to select its parts in the scene; select an object in the scene and the row that holds it is selected here (the menu's *Follow the Scene's Selection*).
- **Build in a New Scene...** (the menu) builds the manifest anew in a fresh scene, keeping or discarding what was adjusted; a kit's setup of that scene (a camera rig, the delivery's look) is a `[ManifestSceneSetup]` method, run for the manifests its kit takes part in (`[ManifestSceneSetup(typeof(MyKit))]`; with none named, the kit compiled beside it) and handed the run's context. What keeps it from running is said in the window's notices. It is refused while a step is locked: a new scene holds nothing of a locked step to leave as it is.

## The Python half: `unitytk/sheets/`

| Part | Does |
|:---|:---|
| `SheetPlan` | The contract (version 2), a typed `SchemaSpec` naming no kit's data: what the plan was read from (`source`: the sheet's and the delivery's file names, each text file's digest, the clause templates' digest, and, once staged, the path the project reaches the settings file by), the steps in sheet order, each with its `fields` (the step's values, named by the reading: `voice`, `placard`, `hint`, `sound`, and `to`: where its own row says it goes by itself) and its rows as actions (`behavior`, `text`, `targets`, `clip`, `to`, `fields`, `settings`, `issues`, `upstream`, `warnings`), and `extensions`, each kit's own data by its name, as the settings file gives it. A row's `fields` are its clause template's groups (`label`, `phrase`, a node group's path: `tool`, `facing`, `side_of`; the hand's `tool`, a pointing row's `arrows`, a list). `from_sheet(sheet, delivery)` reads one; `write` / `load`. Its C# reader is generated (`m3trik/scripts/sync_unity_contracts.py`); `SheetPlan.Field`, `FieldList`, `SetField` and `Extension` read and set those values by name in C#. |
| `ReadingSpec` | How a template's sheet is read, data in `sheets/readings/*.json` (`default.json` every key, `<template>.json` over it): strict or not, the name rules (`inline`, `suffixes`, `viewpoint`, `arrow`), a step ID's shape (`{step}` in a clause template), which step values the plan carries and under which names, the Action cell's words, how a question's options are marked, the phrase matcher's vocabulary, and the column order a sheet in the format is written in. |
| `ReadingSpec.words` (`_cell_reading.py`) | A row of a sheet written in the format (pythontk's [build sheets](../../pythontk/docs/build_sheets.md#rows-a-step-then-what-happens-in-it): a step's own row, then a row per action, an Action word and its Target, With, Clip, Members, Label, To, Settings) read by data, never a phrase: for each word a list of cases, the first whose `if` holds saying which behavior the row is and where each cell goes (`behavior`, `targets`, `fields`, `nodes`, `lists`, `settings`, `pass`, `to`, `clip`, `brings`, `order`, and `until`: how what the row shows goes again, as its span setting says: a picture's `until=B06`, a viewpoint's `ring=step`). Names are found exactly, each issue names its cell by the sheet's own header, a row's order carries no meaning (a word's `order`, a take's `after`), and a step's own row gives the step its To (the plan's `to` field). The reading translates the sheet's words onto the builders' names, so it only shrinks: a builder that takes a word as written needs no case. `tests/test_sheet_spec.py` holds every word and setting the templates declare to a case here, or to its list of named gaps. A project's own reading adds its words. |
| `ClauseBook`, `ClauseSpec` | One row in, the behavior it is out: regex templates (`sheets/clauses/*.json`, and a project's own in a folder beside its settings file), so a project's wording needs no code; each template declares its `roles` (what the reading and the check do with a row of it) and its `nodes` (the groups that name a node). A row no template reads stays in the plan as `unread`. |
| `DeliveryIndex` | The delivery's node paths, takes and object names (`DOOR_GRP`, `DOOR_LOC` and `DOOR_GEO` are the object `DOOR`), read from the FBX by pythontk's `FbxFile`: no DCC, no Unity. A cell's name is looked up exactly (`named`: a node's own name, the end of its path, or a declared alias; ignoring case, the name as written winning, a spelling that differs a warning); a sentence's the tolerant way (`find`: an object name too). |
| `NodeMatcher` | Which node a phrase names, in ordered tiers ("the door" in a step that highlights the red door is the red door; "the top latch" is `LATCH_UPPER`). A tie or a vaguer word is stated, never guessed; a one-letter typo is read past and stated; `aliases` name what no rule finds. |
| `SheetSync` | `sheet.sync`: the plan, the delivery's files and the files its steps name (the reading's `staged` step fields: a step's sound) staged into a Unity project, only what differs written. |

The sheet is read by the Shot Manifest's parser (`Mapping.resolve`), so one sheet builds the DCC's shots and the task alike; its format is pythontk's [build sheets](../../pythontk/docs/build_sheets.md) guide. A sheet in the format is read by its cells (the words' reading, above): no phrase is matched, no name is inferred, the hand is not followed and no viewpoint pattern is asked of a name, since each cell says what it is. The rest of this section is how [a sheet of sentences](../../pythontk/docs/build_sheets.md#a-sheet-of-sentences) is read. A sheet read with a strict reading (`strict: true`: `mapping="interactive"` or `"linear"`) is read row by row (`_row_reading`), each naming rule (inline names, build suffixes, viewpoints, arrows) the reading's `names` where it states one: each row's words bind only to the names that row lists in Asset Names or writes inline, a plural guidance phrase binds every listed name carrying its head noun, a modifier contradicting the matched name is an error, a destination (a `destination` row's target) must match the reading's viewpoint pattern (what it says the user faces, `, facing <object>`, is the action's `facing`, which the kit turns a viewpoint beside it toward), an Action cell reads a row no phrase does, and each animation row's take is its Animation Clip Names cell (or, alone in its step, the step's ID) and is checked against the delivery: its place in the file, its name, the step the export records for it, and what its keys move (another row's names and none of its own is an error, none of its own a warning; a name two rows list counts for neither); a `points` row names the delivery's authored arrow for each target where it has one (its `arrows` field: the reading's `names.arrow` pattern, its `part` group the part, an optional `step` group the step; `DeliveryIndex.arrows_at`), which the kit shows where it was authored, bobbing in place, else makes one; every issue names its cell (the template's own header) and fix, `row 3 (Asset Names): <reason>: <fix>` (a hint line's `(Hint): ...`; `SheetPlan.parse_issue`), and a warning (a row built anyway) is listed apart, in `warnings`. The highlight and fade phrases are clause templates here, worded as pythontk's behavior templates detect them. Any other sheet is read as below. A step's clip rows name their takes as the manifest names its shots: the step's ID for one, `<step>_<n>` for several. The hand is followed as the sheet runs, so a `uses` row done with what the hand holds names it in its hand field (the reading's `hand`, `tool`). No behavior is known by its name: every template, the built-in ones too, takes part by the `roles` it declares (`plural`, `shows`, `points`, `takes`, `uses`, `places`, `releases`, `destination`, `advances`, `continues`, `on_page`, `page`, `entry`, `entered`, `otherwise`, `questions`, `lists`, `ticks`; a role declared with `settings` belongs to the rows carrying them), so a project's own template takes part fully: its behavior is an Action word, its `clip` says it plays a take, and its roles add it to the readings and the checks.

### The strict check

`SheetCheck.run(sheet, delivery=None)` (the operation `sheet.check`: `python -m pythontk ops run sheet.check sheet=<csv> [delivery=<fbx>] [takes=<csv>]`) checks a sheet at each hand-off, needing neither Unity nor a DCC: alone before it goes to the artist (its own names stand for the delivery) and with the exported FBX before delivery. The sheet is parsed once. Each item names its cell (step, row, column by the template's own header), its severity, the reason and a fix: the reading's issues and warnings, plus a column no field takes, a jump back past a take (error) or forward past one (warning), and the checks the clause templates' roles key: a `continues` row beside an `advances` one, an `on_page` row on an empty page, an `entered` row with no `entry` row or no `otherwise` row, a question without exactly one marked option, a `questions` row with no question after it, a `lists` row with no items and no `ticks` rows after it, a tick no list before it holds; an animation row whose take cell is empty (the take to write is the fix: the cells are what give a step a shot in the Shot Manifest), an arrow (`<PART>_ARROW`, the reading's `names.arrow`) whose part the delivery lacks, and a take that ends on the next take's first pose (a part that holds, then jumps there within the take's last second: played alone, the take shows the next step's setup; the item names the row, the frame and where to cut, read from the FBX by pythontk's `FbxFile.take_setup_jumps`). A strict reading fails on an error; the `default` one reports and passes. Every reader takes the Interactive template where none is named (`DEFAULT_TEMPLATE`). `SheetPlan.take_list(sheet)` is the take list the artist builds from (`write_takes` saves it as a CSV). Run it where the sheet lives, never in a public CI run: client sheets stay out of public logs.

### A project's sheet settings

A project keeps a settings file beside its sheet, in the project that owns it (a task's, an animated procedure's, any sheet's) (`SheetSettings`, JSON, paths relative to the file): `sheet`, `mapping`, `deliveries` (the FBX or GLB files the delivery is, in order, read together as one through `DeliveryIndex.merged`; `DeliveryIndex.from_file` reads either), `extras` (files whose nodes join the delivery but whose takes no step plays: an older delivery's arrows, viewpoints, panel anchors), `names` (the project's own name rules over its reading's, validated: `viewpoint`, `arrow` with its `part` group, `inline`, `suffixes`), `aliases` (`{old name: new name}` for renamed nodes, which `DeliveryIndex.named` and `find` read; one that goes round in a cycle is refused), `options` (the template's option values: `{"audio": "narrate"}` gives each step its recording, else its narration, from `recordings/` and `narration/` beside the file, a `pronounce.json` there saying words as written), `retired` (step IDs no step carries again and no jump goes to), `clauses` (the folder of its own clause templates beside the file, `clauses/` by default: never a per-user folder, so the sheet reads the same on every machine; the plan's `clauses` and `clauses_digest` name them, and the manifest says its plan is stale when one changes) and `extensions` (each kit's own data, by its name, carried into the plan as it stands: the Tasks kit's `task.tools`, below). With narration on, `python -m pythontk ops apply narration.render` speaks the sheet's lines (pythontk's [narration](../../pythontk/docs/narration.md)); each plan step's `sound` field is its sound, relative to the file, and the strict check reports a voiced step with none yet and says once how many speak narration standing in for recordings. `SheetSettings.load(path).plan()` reads the project's plan and `.check()` checks it; the operations take it as `settings=<file>`. A tolerant reading stays tolerant under a project's name rules.

### A sheet written before the format

`SheetConverter.convert(sheet, delivery, out)` (the operation `sheet.convert`; `settings=` takes a settings file, `options=` the old template's options) rewrites it in the format (`to=`, the Interactive one by default: its reading's `cell_columns`) from what the tolerant reading bound: a step's own row (its ID, name, voice, placard and audio; a dotted ID respelled with a letter, `B03.5` to `B03A`, every row that goes to it with it), then a row per action with its word, the node names its words named in Target and With (the tool in hand, an authored arrow), its take in Clip and what the take moves beyond those in Members, a button's words in Label and where it goes in To, and its settings (a press held to play `trigger=hold`, a part brought near `trigger=near`). Each row's old wording is kept in its Notes, which nothing reads. What a sentence sheet needed rows for and the format does not is folded away: a step that goes on by itself and a page's buttons need no row, a ring shown and later hidden is its teleport's `ring=` span, a picture hidden later is its `until=`. A row no phrase reads keeps its words and takes no word, and comes back listed by step for a person, as does anything the old sheet does not say (no value is invented). `cells=False` writes the older sheet of sentences instead (the reading's `columns`: Asset Names, Animation Clip Names, Text On Placard).

## The Unity half: `Features/Manifests/` and `Tools/Manifests/`

| Type | Does |
|:---|:---|
| `SheetPlan` | The plan file read through its generated shape (`Read`, `Load`), of the one version this editor reads, or refused whole with what to do. |
| `Manifest` | The asset a sheet's build is kept by: its plan, the delivery's model and extras, the scene, the locked steps, each kit's settings, the behaviors that are off (`off`), where it differs from the sheet (`edits`), each object's own values (`tunes`), what the last build gave each part (`built`), what a person changed on one since (`adjusted`) and the helpers a person moved from where a kit placed them (`moved`). `ManifestsActions.Create(plan)` makes one beside a plan: of the files a plan was read against, the first is its delivery's model and each other one an extra. Its inspector edits what a person sets by hand; the rest changes through the actions alone. |
| `ManifestScene` | The delivery's instance in the scene: a plan path found by the records' name rule (`RecordNames`), the takes its model carries, a file the plan names by its path (`Asset<T>(path)`, under `AssetFolder`, the manifest's `assetFolder` else its plan's folder); and what a build's builders share (the plan, a kit's settings and state, `Hold`: what a row holds). |
| `IManifestBehavior`, `[ManifestBehavior]` | One builder per behavior, found by its attribute wherever it is compiled (`ManifestBehaviors`; its kit, `KitOf`, the one compiled beside its attribute, else beside its builder, and its settings that kit's, `SettingsOf`): `Check` says what keeps a row from being built, `Apply` builds it through the features' own actions. The attribute says what the behavior does (`About`), which of its kit's settings are its own (`Settings`) and which of those are its row's as a whole, never one object's (`RowSettings`), which of its rows' fields a person may set (`Fields`), name nodes (`NodeFields`) or takes (`TakeFields`, the contract's `clip` by default) for an assessment to find, how the window labels them (`FieldLabels`) and what its chip says (`ChipFields`, `Suffix`). |
| `ManifestsActions.SetOff`, `SetAssigned`, `Assignable`, `Effective` | A behavior off for the whole manifest; a behavior given to one object of a step or taken from it; what an object can be given; and the plan as the manifest builds it (the sheet's rows, less what is off, plus what was added). |
| `IManifestKit` | What a kit builds around its rows: `Begin` before any row (what they share), `End` after, `Keep` and `Forget` for what a person adjusted, `Kept` and `Revert` so what it keeps itself (a moved helper) is listed and taken back with the manifest's own adjustments, `PlaceAgain` so what it placed by a search is searched for anew on the next build (`ManifestsActions.PlaceAgain`), `Settings` for its settings type. It takes part in a build of every plan that holds one of its rows, and of no other. |
| `ManifestsActions.Assess`, `Problems` | Each row with whether it can be built, what a build would change for it and what it holds: the management view. Changes nothing. `Problems` says what keeps one row from being built, as its assessment does (the plan's issues on it, a node or take the delivery lacks, its builder's check): a builder asks it of a row its own depends on (a marker of a later teleport's viewpoint). |
| `ManifestsActions.Build` | The kits' shared parts, then each ready row through its behavior's builder, in plan order; the rest raised as issues. A kit makes what its rows need as part of it (the Tasks kit: the twins its fades and highlights draw with, `<plan>.twins.asset`), so nothing is run by hand after a build. A dry run plans, a menu run is one undo step, a second build changes nothing; `only` builds the named steps, and a locked step is left as it is. |
| `ManifestsActions.Reset` | The manifest built anew in a new scene, then the `[ManifestSceneSetup]` methods of the kits taking part; its context asked before the scene is saved. |
| `ManifestsActions.Stale`, `SyncCommand`, `ReadAgain` | Whether the sheet, its settings or a delivery file changed since the plan was read (the settings file read through its generated reader, `SheetSettings.g.cs`; each file's digest kept while its size and last write stay), or what could not be told; the command that reads them again, and `ReadAgain`, which runs it from the editor (`python` found as a terminal finds it, by PATH and PATHEXT, a launcher's `python.bat` shim too, which `cmd` runs with each argument quoted by its rules; else no shell: each argument reaches the reader as written) and says its outcome as the reader rated it (done, staged in part, cancelled: nothing imported, or failed). |
| `ManifestStatus`, `ManifestAssessment` | The statuses with their severity, words and sentence; an assessment's steps, rows, build plan and summary. |
| `ManifestWindow`, `ManifestLines` (`Tools/Manifests/`) | The window, and what it shows as plain lines (a test, or an agent, reads the same lines). |

## Extending it

- **A sheet's own wording** for a known behavior: a clause template in the project's `clauses/` folder, beside its settings file (`SheetSettings.clauses`), no code; it wins a built-in of its name.
- **A new behavior**: its template and a builder, `[ManifestBehavior("<name>", About = "<what a row of it does>")] class X : IManifestBehavior`, in a project's own editor assembly. A builder says what it holds (`scene.Hold(part)`), so the window lists it under the behavior, with Select and Edit; `Settings` names the fields of its kit's settings that are its own, which the window opens as the behavior's settings (`RowSettings` those of them its row has as a whole, read as `scene.Settings(step, "", row)`); `NodeFields` the fields of its rows that name nodes (checked as its targets are; no other field is taken for a node), `FieldLabels` and `ChipFields` how the window shows them. A kit's own attribute derives from `ManifestBehaviorAttribute` to carry what its behaviors say about themselves (the Tasks kit's `[TaskBehavior("inspect", ActsOn = true)]`).
- **A kit**: an `IManifestKit` beside its behaviors, for what they share, and a `ScriptableObject` of its settings.
- **A word the sheet uses for a node**: `from_sheet(..., aliases={"the highlighted area": "LATCH"})`, or the settings file's `aliases`.
