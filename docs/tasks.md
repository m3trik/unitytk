# The Tasks kit: tasks from a build sheet

A task is one kind of scene a [build sheet builds](manifest.md): its rows read as a task's behaviors (take a tool, use it on a part, go to a viewpoint, answer a question on the placard), and the Tasks kit holds the builders for them. The sheet's reader, the strict check, the settings file, the staging (`sheet.sync`) and the Manifest window are the manifest's, described there; this page is what the kit adds: the phrases its rows are written in, what each behavior builds, the building blocks under them, and the sample task.

## The phrases it reads

Beside the guidance phrases (pythontk's), the built-in templates read these, each the behavior in brackets:

| Group | Phrases |
|:---|:---|
| Guidance | `<object> turns on` (turn_on) · `<object> turns amber` / `goes off` / `switches to green`, a default indicator state (set_state) · `Highlighted <object> appears in place` (show) · `Arrow points at <object>` / `Arrows point at <objects>`, the parts in Asset Names (indicate; a Hint's `-Bouncing arrow pointing at <objects>` still reads) |
| Hand | `Selecting <object> places it in hand` (take) · `Return <object> to the table` (return) · `<object> returns to hand` (hold) |
| Animation | `Selecting <target> triggers <Name> Animation`, optionally `with <tool> in hand` / `and returns <tool> to hand` (use) · `Trigger <Name> Animation` (play) · `Moving <held> close to <slot> triggers <Name> Animation` (place) · `Pressing and holding <target> plays <Name> Animation` (use, held to play) |
| Flow | `Auto Advance` (advance) · `Selecting '<Label>' triggers step advancement` (pause) · `... triggers step <ID>` (goto) · `... ends the task` (exit) · `Selecting <object> triggers step advancement` (select) |
| Movement | `User is teleported facing <object>` (teleport: the build finds where they stand), `... to the front of <object>, facing <object>` (or `back`, `left`, `right`, `the other side of`: the side it is found on; front is the object's forward), or `... to <viewpoint>, facing <object>` / `... to <viewpoint>` where the delivery authors one · `The destination marker fades in` / `fades away` (marker; marker, hidden) |
| Placard | `'YES' and 'NO' buttons appear on the placard` (buttons) · `A checklist appears on the placard: '<item>', '<item>'` (checklist) · `Checklist item '<item>' gets a check mark` (check) · `A number pad appears on the placard` (number_pad) · `Entering '<value>' triggers step <ID>` (answer) · `Entering any other number triggers step <ID>` (answer, any other) · `PiP screen shows <view>` (pip) · `PiP screen fades away` (pip, hidden) |
| Action words | Any behavior's word (`use`, `play`, `teleport` ...), `press and hold` (a Use held to play), and `note` for a row for people (a scene's description): nothing is built |
| Quiz | A step with an option written `* <option>` is a question: its placard text the question, its rows no phrase reads its options (option), the starred one `correct` |

A sheet in the format (pythontk's [build sheets](../../pythontk/docs/build_sheets.md): a step's own row, then a row per action) says the same with a word and its cells, read through the reading's `words` (`sheets/readings/default.json`), each word the behavior in brackets:

| Family | Words |
|:---|:---|
| Attention | `highlight` (highlight) · `indicate`, `where=` an arrow an artist made, or an empty object the kit's arrow stands on (its tip on it, pointing along its forward), `size=`, `color=` (indicate) |
| Visibility | `fade_in`, `fade_out` (the same) |
| State | `set` with `state=`, a state the target's indicator has (set_state) |
| Hand | `take`, `return` (the same) |
| Animation | `use`, With the tool in hand (use; `trigger=hold`: held to play; `hold=<seconds>` (with `trigger=hold`, or the default `select`): a timed press; `trigger=near`: place, which takes no `hold`) · `play`, `after=` the take it follows (play) |
| Flow | `button`: To `next` (pause; `when=start` holds the step at its start, the one button that takes `when`), a step's ID (goto), `exit` (exit), `restart` (goto, the first step); with a `retry` button in its step the step is a question, `next` its right option and `retry` a wrong one saying `reply=` (option) · `select` (select) · `answer`, Label `*` any other (answer; the key pad comes with it) |
| Movement | `teleport`, `where=` the viewpoint the user stands on, facing its forward, moved and turned in the scene like any object (one that faces away from the row's Target, what the row says the user is brought to face, is said on the row and never turned for them: `unity.task.faces_away`); with none, the build places one facing the Target, once (teleport; `when=end`: as the step ends; `ring=step` or `ring=<a step>`: the viewpoint's ring on the floor, shown until then, which is the marker's two rows in one) |
| Screen | `pip`, Label its caption (none: what it shows, as the row names it), `until=<a step>` (pip, and its hiding) · `checklist`, `check` (the same) · `note` (nothing is built) |

A step with no choice goes on by itself, and a page's buttons are its `button` rows: neither needs a row. Every setting a word declares reaches its builder under the kit's name for it (a highlight's `style` and `color`: `highlightStyle`, `highlightColor`; a fade's `fade`: `fadeSeconds`; a played take's `speed`: `playSpeed`; a sheet's lower-case choice, `style=pulse`, reads as the choice it spells; `tests/test_sheet_spec.py` holds that none is dropped); a step row's own To is carried in the plan (`to`) and not yet acted on. What a row cannot be built as is said by its builder's check: a `set` on a target with no indicator states, a `use ... trigger=near` whose slot is part of what it places.

## The kit: `Kits/Tasks/`

| Type | Does |
|:---|:---|
| `TaskBuild` | The kit's part of every build of a plan that holds a task's rows (`IManifestKit`): the plan's steps as a `Sequence` (`Task (<task>)`, a step per plan step, each wired anew where its rows changed since it was built), the task's placard where a step shows a page on it, what the hand holds made holdable, the viewpoints the kit places, and the user's rig where the scene has none; after the rows, a page per step with something to show (`TaskSettings.pages`: its placard text, a button, the key pad, a reply; `EveryStep`: each step, its voice line where it has no placard text) and each step's sound; a person's adjusted spots kept in its manifest (`Manifest.moved`, with its other adjustments), only this task's (another plan built into the scene keeps its own). The objects it makes are named by the task's `TaskSettings.names` (`Task`, `Placard`, `PiP`, `Voice`, `Viewpoints`, `Debug`, then the task's: its settings file's name, else its sheet's, so a renamed sheet is the same task; `VIEW_` before a placed viewpoint's step). |
| `TaskKit.MakeRig` | The user, where the scene has no rig of its own (nothing with a `Traveler`), as the settings ask (a manifest's, or those a script hands the scene): the scene's main camera (one made where it has none) gets a `Traveler`, a hand in its view and each input the project has (`Interactions.EquipUser`: a pointer's clicks, and a right-button drag that turns the eyes, `PointerLook`), and starts a little behind the task's first viewpoint. `TaskSettings.rig` is `Desktop` (the default) or `None` (the scene's own); a scene declares a rig of its own by one that travels (a headset's origin given a `Traveler`), which either leaves as it is; `eyeHeight`, `handInView`, `nearClip` (how near the eyes see, so what the hand holds shows whole), `startBack`. A dry run plans the camera it would make and what goes on it (`PlannedObject`), making none. So Build in any scene, a new project's sample scene too, leaves a task a person can play. |
| `TaskKit.AddDebugTools` | A task's debug tools, each a feature's, added by its action (the kit holds no runtime code): the Panels feature's `DebugPanel` (the surface commands go on), the Steps feature's `SequenceDebugCommands` and `SequenceAutopilot`, and the Interaction feature's step actor (`Interactions.AddStepActor`, `InteractionActor`: how the autopilot acts on the task's targets, a required tool taken into the hand first, a press held until its clips end, clips let play or played to their end at once). The autopilot plays a built task through (`fastForward`, `stopAt`: a walk to a step; `Tick`, `Run`, `Log`, `Stuck`). In the editor, persistent calls run only once switched to Editor and Runtime, as the tests do. |
| `[TaskBehavior]` | The manifest's behavior attribute with a task's traits (a builder is an `IManifestBehavior`). The attribute's traits say what kind of row it is, which the rest of the task builds by (`TaskBehaviors.Traits`): `ActsOn` (the user acts on its targets), `Offers` (its label is a button on the page), `EndsStep` (choosing it ends the step: a row after it happens as the step ends), `Chooses` (its step waits on a choice), `GoesOn` (its step goes on by itself whatever it offers: `advance`), `Holds` (the hand holds its targets), `Places` (it names places), `Teleports` (it brings the user to a viewpoint, which the kit places first where the row names none: `teleport`), `Returns` (it sends its targets home: `return`), `Partner` (the behavior its rows pair with, by name: a `check` ticks the latest `checklist`, a `quiz` goes to the first step holding an `option`; either side may name the other, `TaskBehaviors.Pairs`). What needs code to say is an interface on the builder: `IStepGate` (its button holds its step, as it finishes or at its start: `pause`), `ITaskPageContent` (below). The task knows no behavior by its name, so a project's own takes each role the kit's do. |
| `TaskPage`, `ITaskPageContent` | A step's page as its rows fill it: its text, a button per label a row offers, a wrong answer's reply, the key pad, and whether a row puts something else on the placard (a list, a tick, a refusal: `OnPlacard`). A behavior puts its part on the page through `ITaskPageContent` (the kit's `placard`, `number_pad`, `option`, `checklist`, `check`, `use` and `place` do); what the pages hold decides whether the task gets its placard. |
| `Behaviors/` | The builders, one per behavior: [what each builds](#what-each-behavior-builds). |

### What each behavior builds

| Behavior | Builds |
|:---|:---|
| `take`, `hold`, `return`, `select`, `play` | `take`: holdable, target, taken on selection; the step waits for it. `hold`: the tool holdable (a clip lends it and gives it back). `return`: the holdable sent back where it rests as its step ends (`SendHome`). `select`: a selection that completes the step. `play`: a clip after the row before it. |
| `use` | A target requiring the row's tool, playing its clip, the step awaiting its end; the clip is the step's own (a `ClipTrigger` on the target that its step switches on), so a door the task opens early and closes late plays each clip in its own step. A tool the clip does not move goes from the hand to a spot of its own on the part the clip moves (a bolt it turns out): an object under that part (`Work <tool>`, `Interactions.AddWorkSpot`), which it rides while the clip plays, then it comes back. The spot is made on that part's own pivot and axes, the rig's convention (a tool's pivot at its tip, its axes the part's): a tool rigged for its work works as rigged, and the kit guesses nothing from shapes for one that is not. That is a person's to adjust: the rig, in the DCC (its pivot at its tip), or, after a build, the tool's own tip fields in its inspector (`Holdable.tipPosition`, `tipRotation`: for every part it works on), or the spot moved and turned in the scene like any helper (for that part alone); each is kept by every build, listed on its row and put back by Revert. A tool the clip moves is the clip's: it moves from the hand into the clip's first pose, the clip waiting until it is there, and back to the hand as the clip ends, each one eased move of its whole shape (a tool whose pieces the clip turns blends piece by piece), never by way of its table. A `use` row plays its take on a click unless the sheet or the object says otherwise (`TaskSettings.useTrigger`): held to play ("Pressing and holding ...": its clip plays while held and pauses as it is let go, or plays back to its start, `releaseRewinds`), or a timed press (held `pressSeconds`, then it plays). |
| `place` | A slot requiring what the hand holds, playing its clip when selected or once the held thing comes within reach (`SelectNear`); what the clip moves into place stays there as it ends, out of the hand, that place its rest from then on (`ClipPlayer.Entry.leaves`, `Holdable.Leave`; `TaskSettings.placedStays`, on: off, it comes back to the hand as a tool does); a part the clip does not move (its take slides a stand-in home) goes to its own spot on what the clip moves (that part's pivot and axes: the two are rigged alike, or the spot is moved), rides it into place and stays at its work there, out of the hand (`Holdable.StayAtWork`); a slot that is part of what it places would ride into the hand, so its row is unresolved until it names where the part goes. A click on a target that cannot take it (a slot inside the part a step first takes) goes to the target around it that can (`Target.Resolve`). |
| `set_state` | The target's indicator switches to the row's `state` as its step starts, and stays (an `EmissionStateSwitch` on the Emission Track that shows the target's material, `RenderEffectsActions.TrackOf`, which the step enables); the states are the delivery's (off, green, blue, amber, red by default); a target the delivery brought no track for, whose material someone gave an emission by hand, gets its track from the build (`RenderEffectsActions.AddEmissionTrack`: the same default states, declared once in pythontk and generated here, or off and on where its emission is mapped and can only be dimmed), so the kit switches states with no DCC's record; a state the track lacks, or a target that emits nothing, is said by its check; a lit indicator is drawn a glow card so it reads from afar (`IndicatorGlow`). |
| `highlight`, `turn_on` | A glow while the step runs, in the colour and cadence the DCC keys highlights with (pythontk's effect recipe, generated into the package), its colour the row's or the object's own where one is given (`highlightColor`, the sheet's `color`, for either); a `highlight` pulses on a part the task asks the user to act on (a behavior whose rows act on their targets says so: `[TaskBehavior("inspect", ActsOn = true)]`) and glows steady on one it only points out; a `turn_on` glows steady. A cue (a highlight, an arrow) at what its step has the user act on shows while they can act on it: once what it needs is in hand, until they have (`TargetCue`, which its step switches in the cue's place), so a step's keys are pointed out first, then its locks, each lock's arrow gone as its key turns, and nothing glows in the hand; nor is anything pointed out over a take that plays (one arrow at two screws hides while the first is turned out, and comes back for the second); `TaskSettings.cueWhen` (`Ready`; `Step`: for the whole step) says so for a task, a row or an object, and a cue at what the user only looks at shows for the whole step. |
| `fade_in`, `fade_out`, `show` | A fade as the step starts or ends; an object its step also returns goes back shown, the return being how it leaves the hand (`TaskSettings.fadeReturned` fades it too, as the sheet says; the row notes which). `show` is `fade_in`'s builder under a second name, a hidden target fading in as its step starts (its template also highlights it). |
| `indicate` | An arrow at each target while the step runs, placed for the step (`Indicator <step>` under the target): beside it in free space, pointing at it from where the user then stands and sees it, over it where that works, straight out of what the part is mounted on where no other way is free (a latch on a door that opened sideways), riding it as it moves; a flat arrow, glowing in the highlight's colour, that turns about its own axis to face the user wherever they stand, blending to face them whole as they look nearly down its axis. A target that is several things apart ("both latches": one group, two latches) gets an arrow at each (`Placer.Items`: past wrapper nodes, the things that show, those touching joined, up to `Placer.MostItems`). Things closer together than `TaskSettings.arrowMerge` (0.15 m; 0: never) share one arrow, pointed at them all (`Placer.Cluster`: two latches side by side). |
| `teleport` | A viewpoint the step brings the user to as it starts: the row's node where it names one, else its own under `Viewpoints (<task>)`, named as every tool names a row's own helper (`VIEW_<step>_<target>`, the plan's `helpers`; a sheet in the old sentence format gets `VIEW_<step>`, and `VIEW_<step>_<n>` for its step's `n`th such teleport past the first: one as the step starts and one as it ends are a viewpoint each), which the kit places on the floor where what the row faces is seen: within reach of what the rows there have the user act on (`Placer.DefaultReach`), else far enough back to see the part whole; which side of it they stand on is the row's to say, `side`, or the viewpoint's to be moved to; where the row says none, the side out from the delivery's middle, as the Shot Manifest places it. Or as the step ends, where the row comes after the step's `pause`, `goto`, `exit` or `quiz` row ("Selecting 'Next' ...", then "User is teleported ..."). The user stands on the viewpoint as it stands, facing its forward (one the kit placed faces what its row faces, so a person moves and turns it like any object; a viewpoint the row names, where the row also says what they face, stands them toward that, no farther from it than the task's stand-off, `TaskSettings.standOff`, 1.5 m), and a viewpoint's disc is a marker, shown only where a showing `marker` row turns it on. |
| `marker` | A ring on the floor (put up, or, `markerShow` Hide, taken away) (`Marker`) at the row's target, else at the next teleport's viewpoint, on from its step until a hide row's (a hide row in its own step: on while the step runs). A marker of a teleport that cannot be built (a viewpoint the delivery lacks) is held back with it, and says why. |
| `advance` | What every step that offers no choice does without it (the kit gives it as the build ends; a step whose `pause`, `goto`, `exit`, `quiz`, `option` or key pad rows have the user choose waits on that choice; an `advance` row turned off has its step wait, off everywhere none goes on by itself): the step goes on by itself, once it has run long enough for its voice line (else its placard) to be heard (`TaskKit.DwellOf`: the task's `wordsPerSecond`, at least its `minimumDwell`), or, where it has a sound, for that to play out (its length and the task's `voiceTail`). The pace is the task's, one for every step. A step with a sound plays it while it runs (a `SoundCue` under the task's `Voice` object; the step's `sound` field, found by `ManifestScene.Asset<AudioClip>` under `ManifestScene.AssetFolder`, where staging copies the files the plan's steps name at their paths). The same line delivered as a cue in the step's take (the Shot Manifest keys a step's narration onto its first take) is left to the step (`AnimationAudioPlayer.leave`, `AnimationAudioActions.Leave`: every step's that plays it, a step a build leaves as it stands, locked or another's, by its cue), so it plays once, as the step starts, not again when the user sets the take off. |
| `pause`, `goto` | The step's choices (a `pause` holds the step as it finishes, its button offered once its actions are done; or, `pauseWhen` Start, at its start, its button starting them) (a `goto` whose jump the plan says restarts, `PlanAction.restart`, as its reading says a jump to the first step does, starts over: the scene is loaded again); in a step that also asks for an action (take, select, use, press, place), its Next is offered, and its button shown, once those are done. |
| `option`, `quiz` | `option`: a button on the step's page; the right one goes on, a wrong one says the task's `wrongChoiceReply` and stays, unless a `pause`, `goto` or `exit` row of the step offers that label. `quiz`: a choice going to the first later step that asks a question. |
| `number_pad`, `answer` | The page's key pad (the task's `numberKeys`, one pad for every step), each value keyed in going to its row's step, any other to the step of the `answer` row that takes any other (`answerKind` Otherwise). |
| `checklist`, `check` | A list on the placard from its step on, below each page, until the step its `until` names starts (`checklistShow` Hide: every shown thing has a span) (a checklist listing no items lists the items its following check rows tick); a check row ticks its item as its step ends. |
| `pip` | The task's picture-in-picture (put up, or, `pipShow` Hide, taken away) (`PipView`, the task's `pipStyle`: beside the placard, at the delivery's screen (`pipAnchorPattern`, empty by default; `^UI_PIP` for a `UI_PIP` placeholder), or in a corner of the view: the task's one screen) shows the part the row names close up from its step on, cut away from the user's side and captioned with its row's Label, else with what the row's words say it shows (`captionPattern`; a row written in cells is captioned by its Label alone, and has none without one: `captionFrom`), taken from the object its row names as where it is (`where`: a camera an artist set up, used exactly as it stands, with its own field of view, and switched off so it never draws to the screen; a field of view the row sets of its own is said unused), else from a camera the kit places under the part, riding it (`CAM_<step>_<target>`, as the Shot Manifest names it; `PiP <step>` from a sentence sheet: switched off, it never draws to the screen; selected, its preview is the picture): the clearest view of the part (a tiny one with what it sits on), on the user's side among the spots that see it alike (which face of it is worth showing no search knows: the spot is moved, or the row names a camera), until a hide row's step or the next pip row's. That camera's field of view is the row's (`pipFieldOfView`, 1 to 179 degrees; 0: the view's; one outside is brought within it, and said), set on the camera after a build it is kept as the row's. The delivery's authoring anchors, where the task names them (`anchorPattern`, empty by default; `^UI_` for `UI_` placeholders), are hidden (`Placements.HideAnchor`). |

What every builder shares:

- Before any row is built, every row's tool and every take or hold row's targets are made holdable, so a clip lends all it moves. Each target is selectable only while its step runs; a page's reply and keys are its own fields, which a person changes in its inspector.
- The spots the kit places (viewpoints a teleport row names none of, arrows, pictures' cameras, tools' working spots) are found as the scene stands at their step (`Interactions.PosedAfter`: the clips played before it hold their ends, so a door an earlier step opened stands open), every viewpoint first, so each arrow and picture is placed from where the user then stands; each is a `PlacedSpot` keyed by step (the sample's `teleport/A01`, a step's second placed viewpoint `teleport/A01/2`, an arrow's `indicate/<step>/<its part's path>`, a picture's `pip/<step>`): a person moves one in the scene, and the next build keeps it in the manifest (`Manifest.moved`, each spot relative to its part, listed and reverted with the other adjustments) and every build after puts it there, in this scene or one built anew; **Place Again** on its row has the next build search for it anew, the move dropped. A helper the delivery brought and a row names (a viewpoint, an arrow, a camera: its `where`) is marked a placed spot too, placed where its maker has it (`Placements.PlaceGiven`, keyed `where/<its path>`): moved in the scene, it is an adjustment kept, listed and put back like the rest. Where no spot does its job (no floor sees what a teleport faces, no free spot beside a part is seen), the build says so on the row (`TaskKit.SpotCode`) and the spot is the one to adjust; once a person has moved it and the build keeps it, it is no longer said.
- Each placard page comes up where the kit finds it clear of the scene from where its step stands the user (`PlacardPage.ownSpot`, `spot`: beside the eyes, mirrored, nearer or higher, covering the fewest of what the step shows).
- A task's own choices are its `TaskSettings` (stand-off, PiP style, anchor names, reading pace, which steps get a page, a wrong answer's reply, how a tool's name reads and a buttons row splits, number keys, arrow size, the names of what it makes, where its adjustments are kept, whether it gets its debug tools), kept by its manifest and edited in the Manifest window's Setup. A row's or one object's own values go over the settings its behavior lists as its own (its **Settings...**); a take's window and speed (`playFrom`, `playUntil`, `playSpeed`) are a `use`, `place` or `play` row's as a whole, never one of its objects' (the clip player keeps one entry a take, whatever objects the row names: `RowSettings`), so the window offers them for the row alone (**Settings > For Its Row…**) and keeps them under it, and an object the manifest builds as a row of its own (added there, or given a take of its own) keeps them as its own; the rest are the task's alone, one for every row: where a spot is searched for (`standOff`, `viewAngle`: a person moves the spot itself), a step's pace (`wordsPerSecond`, `minimumDwell`, `voiceTail`), the picture's screen (`pipStyle`, `pipAnchorPattern`) and the key pad's keys (`numberKeys`). The defaults assume no one task: no debug tools, no anchors hidden, a placard only where a step shows a page, the desktop rig only where the scene has no rig that travels.
- A build gives a task its rig and its debug tools where its settings ask (`rig`; a manifest's settings, or those a script hands the scene) (`debugTools`, off by default: a task that ships leaves them out; off, a build takes them away, `PanelsActions.RemoveDebugPanel`; `TaskKit.AddDebugTools(plan)` from a script), for the editor and a headset review alike: a panel beside the eyes (`DebugPanel`) with the step it is on, Skip, Back (the scene loaded again, the autopilot walking to the step before at once, so the scene stands as that step found it), Restart and Autopilot (`SequenceDebugCommands` on the panel, its command surface; the Interaction feature's step actor acts for the autopilot; a `DebugCommand` adds a scene's own).

## Whose fix it is: the system's, a setting's, the content's

A build sets a task up from what the sheet and the delivery say, and guesses at nothing they do not: a first placement is plain (a part's own pivot and axes, a clear line of sight, a default distance). So what is off in a built task is one of three things, and each has its own fix:

- **The system's**: the setup or a behavior is wrong for any task (a picture's camera carried off by its card, every arrow of a step shown at once). The fix is in the package, with a test.
- **A build setting**: this task's data needs saying something the build cannot know. It is said before a build (the settings file, the sheet's row, a helper in the delivery) or after one (an object moved in the scene, a field in an inspector, the Manifest window); what is set after a build is kept by every build, listed on its row as *adjusted*, carried into a scene built anew and put back by **Revert**.
- **The content's**: the sheet's rows or the DCC scene (a take that starts from the wrong pose, a row at the wrong part).

| What is off | Before a build | After a build |
|:---|:---|:---|
| A tool works across its part, or with its middle on it: it is rigged with its pivot off its tip, or its axes off the part's (the kit stands a tool's pivot on the part's, axis on axis) | The rig, in the DCC: its pivot at its tip, its axes the part's. (A settings file holds no adjustment: what a kit's extension holds that the kit does not read is said, `TaskKit.ExtensionCode`) | The tool's own `Holdable` fields, Tip Position and Tip Rotation (for every part it works on), or the `Work <tool>` object under one part, moved and turned (for that part) |
| A part put in place stands off its place | The same: the part's fit, or its rig (its pivot and axes as its place's) | The same: its `Holdable` fields, or its `Work <part>` object |
| Where the user stands, or which side of a part | The row's `where`: a viewpoint in the delivery (a sheet of sentences can also name the side: `to the front of`, `the other side of`) | `VIEW_<step>`, moved and turned |
| What a picture shows, and from where | The row's `where`: a camera in the delivery | `PiP <step>` under the part, moved and turned |
| Where an arrow stands | The row's `where`: an arrow, or an empty object, in the delivery | `Indicator <step>` under the part, moved |
| When a highlight or an arrow shows | `cueWhen` in the task's settings, or the row's Settings | The row's **Settings...** in the Manifest window |
| How a take is set off, how long a press is held, what a part does once placed | The row's settings (`trigger`, `hold`), the task's (`useTrigger`, `placedStays`) | The row's **Settings...**, or the part's inspector |
| How fast a take plays, and which part of it | The row's settings (a Play row's `speed`), the task's (`playSpeed`, `playFrom`, `playUntil`) | **Settings > For Its Row…** on any object of the row (one take for all of them), or its entry of the Clip Player: kept as the row's |

## Where each building block goes

The kit composes; the building blocks are features, each its own assemblies, none naming another. A behavior's builder wires them together in the scene through UnityEvents (a target's `onSelected` calling the clip trigger its step switches on, a clip player's `onFinished` signalling the steps), so the wiring is scene data a person sees in the inspector and an agent writes through the same actions. The action that wires takes the sender's event as Unity's own type and lives in the receiving feature (`StepsActions.SignalOn`), and every action takes plain names, so a dry run plans parts not made yet (a part, or a change to one, that the dry run already planned counts as made: `ctx.Planned`).

## The sample task: tested, then played

The package's **Tasks sample** (`Samples~/Tasks`) is a small cabinet task at life size: a sheet in the Interactive format (`cabinet.csv`, read with the `interactive` template and held to the strict check, 0 errors and 0 warnings), the delivery its steps play (`cabinet.fbx`: a cabinet with a hinged door, two latches on its frame, a bolt, a lid and a button at its back, a table with a key and a wrench, a front and a back viewpoint, `VIEW_FRONT` and `VIEW_BACK`, one take per clip row) and the plan read from them (`cabinet.plan.json`). No DCC makes it: its recipe in the workspace's sample sync (`m3trik/scripts/unity_samples/tasks.py`, run in Python, not Maya) writes the delivery with pythontk's `FbxWriter` and the plan with this reader, and `sync_unity_samples.py --check` holds the committed files to it.

Every window the task shows (the placard, the picture, the debug panel) behaves alike: dragged anywhere but a button it swings around the eyes and rises or lowers, and later pages keep that spot (`movable`, on); the pointer over it shows it can move; a bare arrow in its corner folds it to its heading (`collapsible`).

Its demo recipe (`Tools > unitytk > Samples > Task Demo`) builds the scene a person plays: the cabinet on a floor, and its task built by the kit through the task's manifest, with the sample's own settings (`TaskDemoRecipe.Choose`: its debug tools and a page for every step, which the defaults leave out), which gives the scene its user too (the kit's rig: the scene's camera with a `Traveler`, a right-button drag turning the eyes, its clicks sent into the scene, a `Hand` in its view) and its debug tools (a panel beside the eyes: the step, Skip, Back, Restart, Autopilot). The task's own placard comes up in front of the user with each step. The kit's Edit Mode tests (`TaskSampleTests`) build that same scene through the recipe and play it through as a user would: every step entered, every target selected with the right tool, every clip run to its end, the user brought to each viewpoint facing the cabinet, every choice pressed on the placard. So the scene you play is the one the tests passed.

The demo also makes the task's manifest beside its plan (`cabinet.manifest.asset`): `Tools > unitytk > Manifest` shows each row of the sheet with what it built, and builds again after a change.

To play it:

- **In a project with unitytk**: `Window > Package Manager > unitytk > Samples > Tasks > Import`, then `Tools > unitytk > Samples > Task Demo`, then Play.
- **With no project yet**: `python -m pythontk ops apply unity_project.build key=play` makes `Unitytk-play` beside the owned test project: the newest editor, URP, this checkout's package linked, every sample imported (about four minutes once, seconds after). Open it from Unity Hub, then use the menu above. It is yours: no test or agent runs an editor on it, and a rebuild refreshes it only while it is closed.

## Extending it

- **A sheet's own wording** for a known behavior: a clause template in the project's `clauses/` folder, beside its settings file (`SheetSettings.clauses`), no code; it wins a built-in of its name.
- **A new task behavior**: its template and a builder, `[TaskBehavior("<name>")] class X : IManifestBehavior`, in the kit or in a project's own editor assembly; its traits on the attribute (`ActsOn = true`, `Teleports = true`, `Partner = "checklist"`...), `IStepGate` where its button holds its step, and `ITaskPageContent` where its rows put something on the placard. It is the Tasks kit's row wherever it is compiled: the kit's sequence, placard and voices are built around it, and it takes any role a kit's behavior does.
