# The Tasks kit: tasks from a build sheet

A task is one kind of scene a [build sheet builds](manifest.md): its rows read as a task's behaviors (take a tool, use it on a part, travel to a viewpoint, answer a question on the placard), and the Tasks kit holds the builders for them. The sheet's reader, the strict check, the settings file, the staging (`sheet.sync`) and the Manifest window are the manifest's, described there; this page is what the kit adds: the words its rows are written in, the sentences that read as them, what each word builds, the building blocks under them, and the sample task.

## The words it builds

A sheet in the format (pythontk's [build sheets](../../pythontk/docs/build_sheets.md): a step's own row, then a row per action) writes each action as one word and its cells. A word is named for what its family does at its most general; a case of it (an arrow, a fade, a teleport, a picture-in-picture) is a setting's value or the builder's detail, never a word of its own. The plan carries the word as each row's `behavior`, and the kit has one builder for each:

| Family | Word | Cells | Settings |
|:---|:---|:---|:---|
| Attention | `highlight` | Target, Clip | `style` (auto, pulse, steady), `color` |
| | `indicate` | Target | `style` (flat, solid), `size`, `color`, `where` (where each arrow's tip rests) |
| Visibility | `show` | Target, Clip | `fade` (seconds; 0: at once) |
| | `hide` | Target, Clip | `fade` |
| State | `set` | Target | `state` (required) |
| Hand | `take` | Target | |
| | `return` | Target | |
| Animation | `use` | Target, With (what the hand holds), Clip | `trigger` (select, hold, near), `hold` (seconds, with `trigger=hold`) |
| | `play` | Clip | `after` (the take it follows), `speed` |
| Flow | `button` | Label, To | `when` (end, start), `reply` |
| | `select` | Target (a To is not acted on yet) | |
| | `answer` | Label (`*`: any other), To | |
| Movement | `travel` | Target, what the user is brought to face | `when` (start, end), `ring` (a span), `where` (the viewpoint) |
| Screen | `picture` | Target, Label (its caption) | `until` (a span), `where` (the camera) |
| | `list` | Label, an item a line | `until` (a span) |
| | `tick` | Label | |
| Note | `note` | | |

Beside them the plan holds `advance`, the kit's own row: a step that offers no choice goes on by itself, and the row says so where a step that does should too (a sheet of sentences' "Auto Advance"). A row no reading reads is `unread`: nothing builds it.

A setting is written as the sheet names it (`trigger=hold`, `style=steady`, `color=#3399FF`), and its builder reads it under the word's own group of the task's settings (`TaskSettings.use.trigger`, `TaskSettings.highlight.style`: the manifest's [rule](manifest.md#behaviors-several-to-an-object-each-with-a-switch-and-an-editor)); a lower-case choice reads as the choice it spells. A `where` names an object of the delivery, an artist's, and comes in the plan's `fields` (one entry a Target), never as a setting. A **span** says how long a shown thing lasts: `step` (while its step runs) or a step's ID (until that step starts); a picture or a list with none lasts until the next row of its word, and a travel's ring with none is not shown. So no row takes a shown thing away. What a row cannot be built as is said by its builder's check: a `set` on a target with no indicator states, a `use` with `trigger=near` whose Target is part of its With, a span naming no later step.

## The sentences that read as them

A sheet of sentences (one action a row, in the sheet's phrasing) is read into the same words, cells and settings, as its conversion to cells writes them. Beside the guidance phrases (pythontk's), the built-in templates read these, each the word it reads as in brackets:

| Group | Sentences |
|:---|:---|
| Guidance | `Highlight <objects>` / `<objects> is highlighted` (highlight) · `<object> turns on` (highlight, `style=steady`) · `<object> turns amber` / `goes off` / `switches to green`, a default indicator state (set, its `state`) · `<object> fades in` (show) · `<object> fades away` (hide) · `Highlighted <object> appears in place` (show, and highlight) · `Arrow points at <object>` / `Arrows point at <objects>`, the parts in Asset Names (indicate; a Hint's `-Bouncing arrow pointing at <objects>` still reads) |
| Hand | `Selecting <object> places it in hand` (take) · `Return <object> to the table` (return) · `<object> returns to hand` (a note: the row that used it names it in its With) |
| Animation | `Selecting <target> triggers <Name> Animation`, optionally `with <tool> in hand` / `and returns <tool> to hand` (use, its With the tool) · `Pressing and holding <target> plays <Name> Animation` (use, `trigger=hold`) · `Moving <held> close to <slot> triggers <Name> Animation` / `Trigger <Name> Animation when moved close to <slot>` (use, `trigger=near`) · `Trigger <Name> Animation` (play) |
| Flow | `Auto Advance` (advance) · `Selecting '<Label>' triggers step advancement` (button, To `next`) · `... triggers step <ID>` (button, To the step) · `... ends the task` (button, To `exit`) · `Selecting <object> triggers step advancement` (select) · `Entering '<value>' triggers step <ID>` / `Advance to step <ID> when the number <value> is entered` (answer) · `Entering any other number triggers step <ID>` (answer, Label `*`) |
| Movement | `User is teleported facing <object>` (travel, Target the object: the build finds where they stand), `... to the front of <object>, facing <object>` (or `back`, `left`, `right`, `the other side of`: the side it is found on; front is the object's forward), `... to <viewpoint>, facing <object>` / `... to <viewpoint>` where the delivery authors one (travel, `where` the viewpoint); after the step's choice, as the step ends (`when=end`) · `The destination marker fades in` / `fades away` (the next travel's `ring`, its span) |
| Placard | `Placard text reads "<text>"` (its step's page text) · `A checklist appears on the placard: '<item>', '<item>'` (list) · `Checklist item '<item>' gets a check mark` (tick) · `PiP screen shows <part>` / `PiP screen with <part> appears` (picture, captioned with what it shows) · `PiP screen fades away` (the picture's `until`) · `'YES' and 'NO' buttons appear on the placard` (the step's button rows are its buttons, each checked) · `A number pad appears on the placard` (every answer row brings the key pad) |
| Action words | Any word above, in the Action cell for a row no sentence reads, `press and hold` (use, `trigger=hold`), and `note` for a row for people (a scene's description): nothing is built |
| Quiz | A step with an option written `* <option>` is a question: its placard text the question, its options button rows, the starred one To `next`, the rest To `retry`; `Selecting '<Label>' triggers advancement to the quiz` goes to the first later step that asks one |

A sentence the format needs no row for (a picture, a list or a ring taken away, a ring put up, the buttons a page shows, the key pad, a page's text, a tool back in hand) stays in the plan as a `note` row of its words, so every sheet row is still listed, and what it said is carried by the row or step it belongs to.

## The kit: `Kits/Tasks/`

| Type | Does |
|:---|:---|
| `TaskBuild` | The kit's part of every build of a plan that holds a task's rows (`IManifestKit`): the plan's steps as a `Sequence` (`Task (<task>)`, a step per plan step, each wired anew where its rows changed since it was built), the task's placard where a step shows a page on it, what the hand holds made holdable, the viewpoints the kit places, and the user's rig where the scene has none; after the rows, a page per step with something to show (`TaskSettings.pages`) and each step's sound; a person's adjusted spots kept in its manifest (`Manifest.moved`), only this task's (another plan built into the scene keeps its own). The objects it makes are named by the task's `TaskSettings.names` (`Task`, `Placard`, `Picture`, `Voice`, `Viewpoints`, `Debug`, then the task's: its settings file's name, else its sheet's, so a renamed sheet is the same task; `VIEW_` before a placed viewpoint's step where the plan names it no helper). |
| `TaskSettings` | A task's own choices: a group a word that has settings, named as the word, its fields the sheet's settings beside the kit's own for that word (`indicate`: `style`, `size`, `color`, `merge`, `cue`; `use`: `trigger`, `hold`, `rewind`, `refused`, `stays` and its take's `speed`, `start`, `stop`); then the task's alone, one for every row (where a spot is searched for, a step's pace, which steps get a page, the key pad's keys, the rig, the names of what it makes, its debug tools). Kept by the task's manifest and edited in the Manifest window's Setup. |
| `TaskKit.MakeRig` | The user, where the scene has no rig of its own (nothing with a `Traveler`), as the settings ask (a manifest's, or those a script hands the scene): the scene's main camera (one made where it has none) gets a `Traveler`, a hand in its view and each input the project has (`Interactions.EquipUser`: a pointer's clicks, and a right-button drag that turns the eyes, `PointerLook`), and starts a little behind the task's first viewpoint. `TaskSettings.rig` is `Desktop` (the default) or `None` (the scene's own); a scene declares a rig of its own by one that travels (a headset's origin given a `Traveler`), which either leaves as it is; `eyeHeight`, `handInView`, `nearClip`, `startBack`. A dry run plans the camera it would make (`PlannedObject`), making none. So Build in any scene leaves a task a person can play. |
| `TaskKit.AddDebugTools` | A task's debug tools, each a feature's, added by its action (the kit holds no runtime code): the Panels feature's `DebugPanel` (the surface commands go on), the Steps feature's `SequenceDebugCommands` and `SequenceAutopilot`, and the Interaction feature's step actor (`Interactions.AddStepActor`, `InteractionActor`: how the autopilot acts on the task's targets, a required tool taken into the hand first, a press held until its clips end, clips let play or played to their end at once). The autopilot plays a built task through (`fastForward`, `stopAt`: a walk to a step; `Tick`, `Run`, `Log`, `Stuck`). |
| `[TaskBehavior]` | The manifest's behavior attribute with a task's traits (a builder is an `IManifestBehavior`), registered by its word. The traits say what kind of row it is, which the rest of the task builds by: `ActsOn` (the user acts on its targets), `Offers` (its label is a button on the page), `EndsStep` (choosing it ends the step), `Chooses` (its step waits on a choice), `GoesOn` (its step goes on by itself whatever it offers: `advance`), `Holds` (the hand holds its targets: `take`), `Places` (it names places: `travel`), `Travels` (it brings the user to a viewpoint, which the kit places first where the row names none: `travel`), `Returns` (it sends its targets home: `return`), `Partner` (the word its rows pair with: a `tick` ticks the latest `list` that lists it; either side may name the other, `TaskBehaviors.Pairs`). Traits are a row's: `TaskBehaviors.Traits(action, step)` reads what the attribute declares, refined for the row by a builder implementing `ITaskRowTraits` (a `button` To `retry`, or To `next` in a step holding a `retry` one, is a question's answer: it ends no step). What needs code to say is an interface on the builder: `IStepGate` (its button holds its step, as it finishes or at its start; per row, `TaskBehaviors.Gate(action, step)`: a `button` To `next` that answers no question), `ITaskPageContent` (below). A builder branches on its row's cells and settings, and the task knows no behavior by its name, so a project's own takes each role the kit's do. |
| `TaskPage`, `ITaskPageContent` | A step's page as its rows fill it: its text, a button per label a row offers, a wrong answer's reply, the key pad, and whether a row puts something else on the placard (a list, a tick, a refusal: `OnPlacard`). A behavior puts its part on the page through `ITaskPageContent` (the kit's `button`, `answer`, `list`, `tick` and `use` do); what the pages hold decides whether the task gets its placard. |
| `Behaviors/` | The builders, one a word: [what each builds](#what-each-word-builds). |

### What each word builds

| Word | Builds |
|:---|:---|
| `take`, `return`, `select`, `play` | `take`: holdable, target, taken on selection; the step waits for it. `return`: the holdable sent back where it rests as its step ends (`SendHome`). `select`: a selection that completes the step. `play`: its clip, played as the take its `after` names ends (none: the take of the row before it in its step), at its `speed`. What a row's With names is made holdable whatever its word, so a clip lends it and gives it back to the hand. |
| `use` | A target requiring the row's With in hand, playing its clip, the step awaiting its end; the clip is the step's own (a `ClipTrigger` on the target that its step switches on), so a door the task opens early and closes late plays each clip in its own step. Its `trigger` says what sets the take off: `select` (the usual) a click; `hold`, held pressed, it plays while held and pauses as it is let go (or plays back to its start, `use.rewind`), and with a `hold` above 0 a timed press (held that long, it plays; `select` and `near` hold nothing); `near`, what the hand holds brought within reach of the target (`SelectNear`), or a click with it in hand. A With the clip does not move goes from the hand to a spot of its own on the part the clip moves (a bolt it turns out): an object under that part (`Work <tool>`, `Interactions.AddWorkSpot`), which it rides while the clip plays, then it comes back. The spot is made on that part's own pivot and axes, the rig's convention (a tool's pivot at its tip, its axes the part's): a tool rigged for its work works as rigged, and the kit guesses nothing from shapes for one that is not. That is a person's to adjust: the rig, in the DCC (its pivot at its tip), or, after a build, the tool's own tip fields in its inspector (`Holdable.tipPosition`, `tipRotation`: for every part it works on), or the spot moved and turned in the scene (for that part alone); each is kept, listed on its row and put back by Revert. A tool the clip moves is the clip's: it moves from the hand into the clip's first pose, the clip waiting until it is there, and back to the hand as the clip ends, each one eased move of its whole shape, never by way of its table. With `near`, what the clip moves into place stays there as it ends, out of the hand, that place its rest from then on (`ClipPlayer.Entry.leaves`, `Holdable.Leave`; `use.stays`, on: off, it comes back to the hand as a tool does); a part the clip does not move (its take slides a stand-in home) goes to its own spot on what the clip moves and stays at its work there (`Holdable.StayAtWork`); a Target that is part of its With would ride into the hand, so its row is unresolved until it names where the part goes. A target selected without what it needs in hand says so on the placard (`use.refused`). A click on a target that cannot take it (a slot inside the part a step first takes) goes to the target around it that can (`Target.Resolve`). |
| `set` | The target's indicator switches to its `state` as its step starts, and stays (an `EmissionStateSwitch` on the Emission Track that shows the target's material, `RenderEffectsActions.TrackOf`, which the step enables); the states are the delivery's (off, green, blue, amber, red by default); a target the delivery brought no track for, whose material someone gave an emission by hand, gets its track from the build (`RenderEffectsActions.AddEmissionTrack`: the same default states, or off and on where its emission is mapped and can only be dimmed); a state the track lacks, or a target that emits nothing, is said by its check; a lit indicator is drawn a glow card so it reads from afar (`IndicatorGlow`). |
| `highlight` | A glow while the step runs, in the colour and cadence the DCC keys highlights with (pythontk's effect recipe, generated into the package), its colour its `color` (by default the delivery's own highlight colour); `style=auto` pulses on a part the task asks the user to act on (a behavior whose rows act on their targets says so: `[TaskBehavior("inspect", ActsOn = true)]`) and glows steady on one it only points out; `steady` glows steady whatever the task asks of it (a lamp turned on), `pulse` pulses. A cue (a highlight, an arrow) at what its step has the user act on shows while they can act on it: once what it needs is in hand, until they have (`TargetCue`, which its step switches in the cue's place), so a step's keys are pointed out first, then its locks, and nothing glows in the hand, nor is pointed out over a take that plays; its `cue` (`ready`; `step`: for the whole step) says so for a task, a row or an object, and a cue at what the user only looks at shows for the whole step. |
| `show`, `hide` | A fade in as the step starts, or out as it ends, over its `fade` (0: at once); an object its step also returns goes back shown, the return being how it leaves the hand (`hide.returned` hides it too, as the sheet says; the row notes which). |
| `indicate` | An arrow at each target while the step runs, placed for the step under the target (`POINT_<step>_<target>`, the plan's `helpers`; `Indicator <step>` where the plan names none): beside it in free space, pointing at it from where the user then stands and sees it, over it where that works, straight out of what it is mounted on where no other way is free, riding it as it moves; `style=flat` (the usual) a flat arrow that turns about its own axis to face the user wherever they stand, blending to face them whole as they look nearly down its axis, `solid` the same from every side; its `size` and `color` (the highlight's, by default). A target's `where` is an arrow an artist made, shown where it stands, or an empty object the kit's arrow stands on (its tip on it, pointing along its forward). A target that is several things apart ("both latches": one group, two latches) gets an arrow at each (`Placer.Items`). Things closer together than its `merge` (0.15 m; 0: never) share one arrow, pointed at them all (`Placer.Cluster`: two latches side by side). |
| `travel` | A viewpoint the step brings the user to as it starts, or, `when=end`, as it ends, once its choice is made. The viewpoint is the row's `where` where it names one, stood on exactly as it stands, facing its forward, and moved and turned in the scene like any object (one that faces away from the row's Target, what the user is brought to face, is said on the row and never turned for them: `unity.task.faces_away`); else the kit's own under `Viewpoints (<task>)`, named as every tool names a row's own helper (`VIEW_<step>_<target>`, the plan's `helpers`; `VIEW_<step>`, and `VIEW_<step>_<n>` for its step's `n`th such travel past the first, where the plan names none), which the kit places on the floor where the Target is seen: within reach of what the rows there have the user act on (`Placer.DefaultReach`), else far enough back to see it whole; on the side the row says (`side`), else the side out from the delivery's middle, as the Shot Manifest places it. The user stands on it as it stands, facing its forward (one the kit placed faces what its row faces); how far back a placed one stands is the task's (`TaskSettings.standOff`, 1.5 m at least, and `viewAngle`). A viewpoint the kit places, and one with a mesh of its own (a destination disc), carries a ring on its floor (`Marker`), shown for the row's `ring` (a span) and off otherwise. A travel's viewpoint the delivery lacks is unresolved, and the build goes on. |
| `button` | A button on the step's page, its Label, going where its To says: `next` on, a step's ID to that step, `exit` to the task's end, `restart` to its start again (the scene loaded again: nothing a take did stands), `retry` nowhere (the step stays, saying its `reply`). A step holding a `retry` button is a question: its buttons are its answers, the right one To `next`, a wrong one To `retry`. A button To `next` that answers no question holds its step: as it finishes (`when=end`, the usual), offered once its actions are done, or at its start (`when=start`), the button starting them; in a step that also asks for an action (take, select, use), it is offered, and its button shown, once those are done. |
| `answer` | The page's key pad (the task's `numberKeys`, one pad for every step: every answer row puts it on its page), each value keyed in going where its row's To says, a Label of `*` taking any value no other answer of the step names. |
| `list`, `tick` | A list on the placard (its Label, an item a line; a list with none lists the items its following tick rows tick), below each page, from its step on for its `until` (none: until the next list's step, whose list replaces it); a tick row ticks its item as its step ends, on the latest list before it that lists it. |
| `picture` | The task's picture (`PipView`, the task's `picture.style`: beside the placard, at the delivery's screen (`picture.anchor`, empty by default; `^UI_PIP` for a `UI_PIP` placeholder), or in a corner of the view: the task's one screen) shows the part the row names close up from its step on, for its `until` (none: until the next picture row's step), cut away from the user's side and captioned with its row's Label (none: no caption), taken from the camera its row names as where it is (`where`: one an artist set up, used exactly as it stands, with its own field of view, and switched off so it never draws to the screen; a field of view the row sets of its own is said unused), else from a camera the kit places under the part, riding it (`CAM_<step>_<target>`, as the Shot Manifest names it; `PiP <step>` where the plan names none; switched off, its preview the picture): the clearest view of the part, on the user's side among the spots that see it alike (which face is worth showing no search knows: the spot is moved, or the row names a camera). That camera's field of view is its `fieldOfView` (1 to 179 degrees; 0: the view's; one outside is brought within it, and said), and one set on the camera after a build is kept as the row's. The delivery's authoring anchors, where the task names them (`anchorPattern`, empty by default; `^UI_` for `UI_` placeholders), are hidden (`Placements.HideAnchor`). |
| `advance` | What every step that offers no choice does without it (the kit gives it as the build ends; a step whose button or answer rows have the user choose waits on that choice; an `advance` row turned off has its step wait, off everywhere none goes on by itself): the step goes on by itself, once it has run long enough for its voice line (else its placard) to be heard (`TaskKit.DwellOf`: the task's `wordsPerSecond`, at least its `minimumDwell`), or, where it has a sound, for that to play out (its length and the task's `voiceTail`). The pace is the task's, one for every step. A step with a sound plays it while it runs (a `SoundCue` under the task's `Voice` object; the step's `sound` field, found by `ManifestScene.Asset<AudioClip>` under `ManifestScene.AssetFolder`, where staging copies it). The same line delivered as a cue in the step's take (the Shot Manifest keys a step's narration onto its first take) is left to the step (`AnimationAudioPlayer.leave`, `AnimationAudioActions.Leave`), so it plays once, as the step starts, not again when the user sets the take off. |
| `note` | Nothing: a row for people. |

What every builder shares:

- Before any row is built, every row's With and every take row's targets are made holdable, so a clip lends all it moves. Each target is selectable only while its step runs; a page's reply and keys are its own fields, which a person changes in its inspector.
- The spots the kit places (viewpoints a travel row names none of, arrows, pictures' cameras, tools' working spots) are found as the scene stands at their step (`Interactions.PosedAfter`: a door an earlier step opened stands open), every viewpoint first, so each arrow and picture is placed from where the user then stands; each is a `PlacedSpot` keyed by step (the sample's `travel/A01`, a step's second placed viewpoint `travel/A01/2`, an arrow's `indicate/<step>/<its part's path>`, a picture's `picture/<step>`): a person moves one in the scene, and the next build keeps it in the manifest (`Manifest.moved`, each spot relative to its part, listed and reverted with the other adjustments) and every build after puts it there, in this scene or one built anew; **Place Again** on its row has the next build search for it anew, the move dropped. A helper the delivery brought and a row names (a viewpoint, an arrow, a camera: its `where`) is marked a placed spot too, placed where its maker has it (`Placements.PlaceGiven`, keyed `where/<its path>`): moved in the scene, it is an adjustment kept, listed and put back like the rest. Where no spot does its job (no floor sees what a travel faces, no free spot beside a part is seen), the build says so on the row (`TaskKit.SpotCode`) and the spot is the one to adjust; once a person has moved it and the build keeps it, it is no longer said.
- Each placard page comes up where the kit finds it clear of the scene from where its step stands the user (`PlacardPage.ownSpot`, `spot`), covering the fewest of what the step shows.
- A row's or one object's own values go over the word's group of the task's settings (its **Settings...**), kept by the group's names (`indicate.size`); a take's window and speed (`use.start`, `use.stop`, `use.speed`; a `play` row's own) and a travel's `when` and `ring` are a row's as a whole, never one of its objects' (`RowSettings`), so the window offers them for the row alone (**Settings > For Its Row…**) and keeps them under it. The rest are the task's alone, one for every row: where a spot is searched for (`standOff`, `viewAngle`: a person moves the spot itself), a step's pace (`wordsPerSecond`, `minimumDwell`, `voiceTail`), the picture's screen (`picture.style`, `picture.anchor`) and the key pad's keys (`numberKeys`). The defaults assume no one task: no debug tools, no anchors hidden, a placard only where a step shows a page, the desktop rig only where the scene has no rig that travels.
- A build gives a task its rig and its debug tools where its settings ask (`rig`; a manifest's settings, or those a script hands the scene) (`debugTools`, off by default: a task that ships leaves them out; off, a build takes them away, `PanelsActions.RemoveDebugPanel`; `TaskKit.AddDebugTools(plan)` from a script), for the editor and a headset review alike: a panel beside the eyes (`DebugPanel`) with the step it is on, Skip, Back (the scene loaded again, the autopilot walking to the step before at once, so the scene stands as that step found it), Restart and Autopilot (`SequenceDebugCommands` on the panel, its command surface; the Interaction feature's step actor acts for the autopilot; a `DebugCommand` adds a scene's own).

## Whose fix it is: the system's, a setting's, the content's

A build sets a task up from what the sheet and the delivery say, and guesses at nothing they do not: a first placement is plain (a part's own pivot and axes, a clear line of sight, a default distance). So what is off in a built task is one of three things, and each has its own fix:

- **The system's**: the setup or a behavior is wrong for any task (a picture's camera carried off by its card, every arrow of a step shown at once). The fix is in the package, with a test.
- **A build setting**: this task's data needs saying something the build cannot know. It is said before a build (the settings file, the sheet's row, a helper in the delivery) or after one (an object moved in the scene, a field in an inspector, the Manifest window); what is set after a build is kept by every build, listed on its row as *adjusted*, carried into a scene built anew and put back by **Revert**.
- **The content's**: the sheet's rows or the DCC scene (a take that starts from the wrong pose, a row at the wrong part).

| What is off | Before a build | After a build |
|:---|:---|:---|
| A tool works across its part, or with its middle on it: it is rigged with its pivot off its tip, or its axes off the part's (the kit stands a tool's pivot on the part's, axis on axis) | The rig, in the DCC: its pivot at its tip, its axes the part's. (A settings file holds no adjustment: what a kit's extension holds that the kit does not read is said, `TaskKit.ExtensionCode`) | The tool's own `Holdable` fields, Tip Position and Tip Rotation (for every part it works on), or the `Work <tool>` object under one part, moved and turned (for that part) |
| A part put in place stands off its place | The same: the part's fit, or its rig (its pivot and axes as its place's) | The same: its `Holdable` fields, or its `Work <part>` object |
| Where the user stands, or which side of a part | The row's `where`: a viewpoint in the delivery (a sheet of sentences can also name the side: `to the front of`, `the other side of`) | `VIEW_<step>_<target>` (else `VIEW_<step>`), moved and turned |
| What a picture shows, and from where | The row's `where`: a camera in the delivery | `CAM_<step>_<target>` (else `PiP <step>`) under the part, moved and turned |
| Where an arrow stands | The row's `where`: an arrow, or an empty object, in the delivery | `POINT_<step>_<target>` (else `Indicator <step>`) under the part, moved |
| When a highlight or an arrow shows | `highlight.cue`, `indicate.cue` in the task's settings | The row's **Settings...** in the Manifest window |
| How a take is set off, how long a press is held, what a part does once placed | The row's settings (`trigger`, `hold`), the task's (`use.trigger`, `use.hold`, `use.stays`) | The row's **Settings...**, or the part's inspector |
| How fast a take plays, and which part of it | The row's settings (a Play row's `speed`), the task's (`use.speed`, `use.start`, `use.stop`; `play.speed`...) | **Settings > For Its Row…** on any object of the row (one take for all of them), or its entry of the Clip Player: kept as the row's |

## Where each building block goes

The kit composes; the building blocks are features, each its own assemblies, none naming another. A behavior's builder wires them together in the scene through UnityEvents (a target's `onSelected` calling the clip trigger its step switches on, a clip player's `onFinished` signalling the steps), so the wiring is scene data a person sees in the inspector and an agent writes through the same actions. The action that wires takes the sender's event as Unity's own type and lives in the receiving feature (`StepsActions.SignalOn`), and every action takes plain names, so a dry run plans parts not made yet (a part, or a change to one, that the dry run already planned counts as made: `ctx.Planned`).

| Block | Home |
|:---|:---|
| What a user selects (`Target`), holds (`Holdable`, `Hand`); clips played on demand, each kept at its end (`ClipPlayer`) | `Features/Interaction` (built; the kit's `take`, `use` and `return` builders compose it). A tool's every move (into the hand, to its work, into a clip, back) is one eased move from where it is to where it belongs: `Holdable.travelSeconds` (0.4 s; 0: there at once), `ease` (its curve), `paced` (a long way takes longer, up to twice) and `approach` (0: straight there; above 0, lined up along its tip's axis first). A clip plays the stretch in which it moves anything, never the poses a tool pops into around its work (`ClipPlayer.Entry.from` / `until`, found from the take by `Interactions.Window` while `auto` is on, set by hand when it is off), at its `speed`, and waits at its first pose for its tool to arrive (`waits`). |
| Steps in sequence (`Sequence`, `Step`): each completes on the signals it awaits (a clip's end, a selection), goes on by itself or by a choice, enables its targets only while it runs (`activates`), and enables what it ends with as it ends (`ends`: a tool sent back, a fade) | `Features/Steps` (built) |
| Highlights and fades a step turns on: a `Highlight` enabled while the step runs, a `FadeTo` enabled as it starts or ends (`show`, `hide`) | `Features/RenderEffects` (`AddHighlight`, `AddFadeTo`) |
| The arrow an `indicate` row shows (`Indicator`: over its target's top, pointing down, an authored arrow or the kit's own, flat or solid, or placed beside it, riding it), and a viewpoint's ring (`Marker`) | `Features/Indicators` (built) |
| Where a viewpoint, a picture's camera and an arrow go, found in the scene as a step sees it (`Placer`: line of sight past the scene's meshes; `PlacedSpot`), and a person's adjustment kept (`Placements.Capture`, into the manifest) | `Features/Placement` (built). The search is `SpotPlacementModel`, pythontk's `SpotPlacement` ported and held to its golden cases, so a first pose here is the one each DCC's Shot Manifest makes. A spot the user stands on is found with room to stand, clear of where things come to stand later (a door's reach once a later step opens it), and far enough back to see what it faces whole (`TaskSettings.standOff`, `viewAngle`); an arrow, a picture and a placard's page are placed from where the user then stands, facing the way they were turned when they arrived. |
| Viewpoints a user is brought to (`TravelTo` on the delivery's node: they stand on it, facing its +Z; `Traveler` on the user's rig, a desktop camera or a headset's origin, found as the step runs) | `Features/Viewpoints` (built) |
| The placard | `Features/Panels` (built): a UI Toolkit world-space panel (`Placard`: a heading, a text and a button per choice, its layout `Placard.uxml` and theme `Panels.uss` editable in UI Builder) that comes up in front of the user's eyes as it shows a page, and a `PlacardPage` per step the step switches on while it runs. The kit builds one per task (`TaskKit.PlacardName`): each page's text is the sheet's placard column, else its voice line; its buttons are the step's `button` rows (a wrong answer's reply: `PlacardPage.replies`), an `answer` row's key pad (`PlacardPage.keys`, its Enter choosing what was keyed in), and a `list` row's list (`PlacardList`, ticked by a `PlacardTick`) stays below the pages, pressed into the sequence (`StepsActions.ChooseOn`, `Sequence.Pick`). `PanelsActions.SetUpInput` takes a pointer through the camera and a headset's controller (with the XR Interaction Toolkit's `XR UI Toolkit Manager` in the scene, XRI 3.2+) alike |
| Narration, a picture | `Features/AnimationAudio` (`SoundCue`), `Features/Panels` (`PipView`, a `PipShot` a picture row) (built) |
| Desktop and VR input | Interaction's input doors, each wiring every target as it is made: the uGUI door (built) for a mouse or a touch through Unity's EventSystem (`PointerSelect`; `PointerActions.SetUpPointer(camera)` once per scene: a `PhysicsRaycaster`, a `PointerAssist` (a click that misses every target in play selects the one nearest it within `PointerAssist.DefaultAngle`, 4 degrees, that nothing hides: a latch a few pixels wide takes one click), and an EventSystem where the scene has none, made as Unity's menu makes it, with the input module the project's input handling uses), the XRI door (built) for a headset's controllers (each target the toolkit's `XRSimpleInteractable`, its select passed to the target for the `Hand` on that controller: put a hand on each controller). A held tool's colliders are off, so it never catches a click aimed past it |

## The sample task: tested, then played

The package's **Tasks sample** (`Samples~/Tasks`) is a small cabinet task at life size: a sheet in the Interactive format (`cabinet.csv`, read with the `interactive` template and held to the strict check, 0 errors and 0 warnings), the delivery its steps play (`cabinet.fbx`: a cabinet with a hinged door, two latches on its frame, a bolt, a lid and a button at its back, a table with a key and a wrench, a front and a back viewpoint, `VIEW_FRONT` and `VIEW_BACK`, one take per clip row) and the plan read from them (`cabinet.plan.json`). No DCC makes it: its recipe in the workspace's sample sync (`m3trik/scripts/unity_samples/tasks.py`, run in Python, not Maya) writes the delivery with pythontk's `FbxWriter` and the plan with this reader, and `sync_unity_samples.py --check` holds the committed files to it.

Every window the task shows (the placard, the picture, the debug panel) behaves alike: dragged anywhere but a button it swings around the eyes and rises or lowers, and later pages keep that spot (`movable`, on); the pointer over it shows it can move; a bare arrow in its corner folds it to its heading (`collapsible`).

Its demo recipe (`Tools > unitytk > Samples > Task Demo`) builds the scene a person plays: the cabinet on a floor, and its task built by the kit through the task's manifest, with the sample's own settings (`TaskDemoRecipe.Choose`: its debug tools and a page for every step, which the defaults leave out), which gives the scene its user too (the kit's rig: the scene's camera with a `Traveler`, a right-button drag turning the eyes, its clicks sent into the scene, a `Hand` in its view) and its debug tools (a panel beside the eyes: the step, Skip, Back, Restart, Autopilot). The task's own placard comes up in front of the user with each step. The kit's Edit Mode tests (`TaskSampleTests`) build that same scene through the recipe and play it through as a user would: every step entered, every target selected with the right tool, every clip run to its end, the user brought to each viewpoint facing the cabinet, every choice pressed on the placard. So the scene you play is the one the tests passed.

The demo also makes the task's manifest beside its plan (`cabinet.manifest.asset`): `Tools > unitytk > Manifest` shows each row of the sheet with what it built, and builds again after a change.

To play it:

- **In a project with unitytk**: `Window > Package Manager > unitytk > Samples > Tasks > Import`, then `Tools > unitytk > Samples > Task Demo`, then Play.
- **With no project yet**: `python -m pythontk ops apply unity_project.build key=play` makes `Unitytk-play` beside the owned test project: the newest editor, URP, this checkout's package linked, every sample imported (about four minutes once, seconds after). Open it from Unity Hub, then use the menu above. It is yours: no test or agent runs an editor on it, and a rebuild refreshes it only while it is closed.

## Extending it

- **A sheet's own wording** for a known word: a clause template in the project's `clauses/` folder, beside its settings file (`SheetSettings.clauses`), no code; it wins a built-in of its name.
- **A new word**: its template and a builder, `[TaskBehavior("<word>")] class X : IManifestBehavior`, in the kit or in a project's own editor assembly; its traits on the attribute (`ActsOn = true`, `Travels = true`, `Partner = "list"`...), `ITaskRowTraits` where one row of it differs from another, `IStepGate` where its button holds its step, and `ITaskPageContent` where its rows put something on the placard; its settings a group of its kit's settings named as the word, where it has any. It is the Tasks kit's row wherever it is compiled: the kit's sequence, placard and voices are built around it, and it takes any role a kit's behavior does. A new word is built from the primitives the kit already builds; a builder is added only for a kind of primitive none covers.
